# Bank Services

## 1. Purpose

This document defines the application services of the **Bank** subdomain of the NexusMarket Marketplace Information Management System.

The Bank subdomain manages monetary value: the bank accounts that hold balance on behalf of marketplace participants and the transfers that move money between them.

It provides the settlement layer used by the rest of the marketplace:

```text
Order Payment (Invoicing)  -->  Buyer pays into Marketplace account
Seller Payout (Invoicing)  -->  Marketplace pays into Seller account
Refund (Returns/Refunds)   -->  Marketplace pays back into Buyer account
```

The main business capabilities are:

```text
Open Bank Account
Consult Bank Account
Deposit Funds
Withdraw Funds
Execute Transfer
Consult Transfer History
Block Bank Account
Unblock Bank Account
Close Bank Account
```

This document describes Domain/Application behavior and its interaction with Input Ports and Output Ports. REST DTOs, persistence entities, controllers, JPA mappings, SQL, MongoDB, and infrastructure-specific implementations remain outside this layer.

---

# 2. Domain Model Context

## 2.1 BankAccount

A `BankAccount` holds a single authoritative balance (`currentBalance`) denominated in one `Currency`.

```text
BankAccount
 ├── accountNumber : String
 ├── holder        : Person
 ├── currency      : Currency
 ├── currentBalance : BigDecimal
 ├── status        : BankAccountStatus
 └── openingDate   : LocalDateTime
```

- `currentBalance` is the authoritative record of "how much" the account holds.
- Balance is never derived; every mutation must go through the domain so that invariants are enforced atomically.
- A `BankAccount` belongs to one holder represented as a `Person` Domain Model.

## 2.2 Transfer

A `Transfer` relocates monetary value between two symmetric `BankAccount` Domain Models (source and destination).

```text
Transfer
 ├── transferId    : String
 ├── source        : BankAccount
 ├── destination   : BankAccount
 ├── amount        : BigDecimal
 ├── currency      : Currency
 ├── executionDate : LocalDateTime
 └── status        : TransferStatus
```

Every `Transfer` mutates both `currentBalance` values in the same consistent business transaction/process.

## 2.3 Value Objects

```text
BankAccountStatus: ACTIVA, BLOQUEADA, CERRADA
TransferStatus:   EJECUTADA, RECHAZADA
Currency:         COP, USD
```

The acting `User`, when applicable, exposes:

```text
User
 ├── status : UserStatus
 └── role   : SystemRole
```

Business operations generated by Bank services use:

```text
Operation.operationType : OperationType
```

Relevant operation types include:

```text
BANK_ACCOUNT_OPENING
BANK_ACCOUNT_DEPOSIT
BANK_ACCOUNT_WITHDRAWAL
BANK_ACCOUNT_BLOCKING
BANK_ACCOUNT_UNBLOCKING
BANK_ACCOUNT_CLOSING
BANK_TRANSFER
```

# 3. Authoritative Design Rules

## 3.1 Domain-first

Bank services operate on Domain Models and Value Objects.

They must not receive:

- REST Request DTOs.
- Persistence entities.
- Primitive identifiers as substitutes for Domain Models.
- Individual attributes when the corresponding Domain Model exists.

Correct:

```java
Transfer executeTransfer(BankAccount source, BankAccount destination,
                         BigDecimal amount, Currency currency);
```

Incorrect:

```java
Transfer executeTransfer(String sourceNumber, String destinationNumber,
                         BigDecimal amount, String currencyCode);
```

The application/adapter layer is responsible for translating external representations into Domain Models before invoking the Input Port.

## 3.2 Enrichment before business validation

When the supplied Domain Model does not contain authoritative information required by the use case, the service resolves the corresponding Domain Model through an Output Port.

The general pattern is:

```text
Input Domain Models
        |
        v
Resolve authoritative entities
        |
        v
Validate relationships and business rules
        |
        v
Execute domain behavior (atomic balance mutation)
        |
        v
Persist
        |
        v
Register Operation + Audit
        |
        v
Return Domain Model
```

## 3.3 Output Ports

A Bank service must never access infrastructure directly.

```text
Bank Service
       |
       v
Output Port
       |
       v
Output Adapter
       |
       v
External Resource
```

Typical Bank dependencies are:

```text
BankAccountRepositoryPort
UserRepositoryPort
BusinessConfigurationPort
```

Additional authorization, notification, operation, or audit capabilities are used as separate Output Ports when required by the business rules.

# 5. Open Bank Account

## 5.1 Description

Creates a new bank account for a marketplace participant and establishes its initial status and balance.

## 5.2 Reference

```text
Open Bank Account
    +--> Description
    |       Creates a BankAccount with an initial credit.
    +--> Input Domain Models
    |       holder : Person
    |       initialAmount : BigDecimal
    |       currency : Currency
    +--> Entity Enrichment
    |       Resolve holder when only an identifier is supplied.
    +--> Existence Validation
    |       Only one active account per holder+currency is allowed.
    +--> Related Entity Validation
    |       Not applicable (no related entities).
    +--> Relationship / Ownership Validation
    |       The requester must be the holder or an administrator.
    +--> Actor / Authorization Validation
    |       REGISTERED_USERS / ADMINISTRADOR.
    +--> Domain Validation
    |       - Initial amount >= 0.
    |       - Currency must be supported by the platform.
    +--> Domain Behavior
    |       Create BankAccount with status ACTIVA, currentBalance = initialAmount.
    +--> Persistence
    |       BankAccountRepositoryPort.save(account)
    +--> Operation
    |       BANK_ACCOUNT_OPENING
    +--> Audit
    |       RegisterAuditEvent user, operation, timestamp, details.
    +--> Exceptions
    |       DuplicateBankAccountException, InvalidAmountException.
    +--> Return Value
    |       BankAccount
```

# 9. Execute Transfer

## 9.1 Description

Moves monetary value between two symmetric `BankAccount` Domain Models as an atomic operation.

`ExecuteTransferService` is referenced by the Shipping subdomain documentation as the reference for symmetric balance mutations: "Unlike `ExecuteTransferService`, dispatch does not move monetary value between two symmetric assets".

## 9.2 Reference

```text
Execute Transfer
    +--> Description
    |       Executes an atomic credit/debit between source and destination.
    +--> Input Domain Models
    |       source : BankAccount
    |       destination : BankAccount
    |       amount : BigDecimal
    |       currency : Currency
    +--> Entity Enrichment
    |       Resolve both authoritative BankAccount instances.
    +--> Existence Validation
    |       Both accounts must exist.
    +--> Related Entity Validation
    |       Currencies must match the transfer currency.
    +--> Relationship / Ownership Validation
    |       Source must belong to the acting user unless performed by staff.
    +--> Actor / Authorization Validation
    |       holder of source / ADMINISTRADOR.
    +--> Domain Validation
    |       - Amount > 0.
    |       - Source must be ACTIVA.
    |       - Destination must be ACTIVA.
    |       - Source currentBalance >= amount.
    |       - Source and destination must not be the same account.
    +--> Domain Behavior
    |       source.withdraw(amount);
    |       destination.deposit(amount);
    |       create Transfer(EJECUTADA).
    |       If any step fails the whole operation is rejected.
    +--> Persistence
    |       Save both accounts and the Transfer atomically.
    +--> Operation
    |       BANK_TRANSFER
    +--> Audit
    |       RegisterAuditEvent with amounts and accounts.
    +--> Exceptions
    |       InsufficientBalanceException, InvalidTransferException,
    |       BankAccountBlockedException.
    +--> Return Value
    |       Transfer
```

# 11. Block / Unblock / Close Bank Account

## 11.1 Block Bank Account

Changes the operational status of an account to `BLOQUEADA` and records the operation. Performed by an administrator or staff with authorization.

```text
Domain Validation:
    - Account must be ACTIVA.
Domain Behavior:
    account.block();
Persistence:
    BankAccountRepositoryPort.save(account)
Operation:
    BANK_ACCOUNT_BLOCKING
```

## 11.2 Unblock Bank Account

Restores a blocked account to `ACTIVA`.

```text
Domain Validation:
    - Account must be BLOQUEADA.
Domain Behavior:
    account.unblock();
Operation:
    BANK_ACCOUNT_UNBLOCKING
```

## 11.3 Close Bank Account

Permanently closes an account. Only accounts with `currentBalance == 0` can be closed.

```text
Domain Validation:
    - Account must be ACTIVA or BLOQUEADA.
    - currentBalance must be zero.
Domain Behavior:
    account.close();
Operation:
    BANK_ACCOUNT_CLOSING
```

Both block/unblock/close operations additionally perform `Actor / Authorization Validation` (ADMINISTRADOR) and `Audit` registration.

# 15. Architectural Constraints

The following rules are mandatory for the Bank subdomain:

1. The balance mutation invariants belong exclusively to `BankAccount`.
2. A `Transfer` is an atomic two-sided operation; partial execution must never persist.
3. Negative balance must never be allowed under any circumstances.
4. Transfer execution must reference both `BankAccount` Domain Models, not primitive identifiers.
5. Every settlement-relevant mutation (deposit/withdraw/transfer) generates an Operation and Audit event.
6. Bank services are separate from Order/Invoice services: an order payment may trigger a transfer, but a Bank service never manipulates an `Order`.
7. The Domain must remain independent of REST and security frameworks.
8. The Bank subdomain must be fully testable without requiring infrastructure components.

# 16. Consistency Rules

The Bank Services document must remain synchronized with:

1. `BankAccount` Domain Model.
2. `BankAccountStatus`.
3. `Transfer` Domain Model.
4. `TransferStatus`.
5. `Currency`.
6. `OperationType` and Operation/Audit services.
7. Authorization rules.

## 16.1 Implementation is authoritative for implemented behavior

When documenting a service that already has an implementation, the implementation is the source of truth for processing order, entity enrichment, validations, state assignment, repository calls, operation creation, and audit details.

## 16.2 Specification is authoritative for intended behavior not yet implemented

For services without a concrete implementation, this document describes the behavior established by the current domain/service specification. Such behavior must be verified against the implementation before being treated as implemented functionality.
