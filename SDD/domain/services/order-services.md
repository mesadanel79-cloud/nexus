# Order Services

## Introduction

This document defines the services belonging to the **Order** subdomain of the NexusMarket Marketplace Information Management System.

The services in this subdomain are responsible for managing the lifecycle of orders placed by customers, from the initial creation through evaluation, confirmation or cancellation, fulfillment, payment, and closure.

Orders are represented by the `Order` Domain Model and inherit from `MarketplaceAsset`.

```text
MarketplaceAsset
      │
      └── Order
```

An order is a marketplace asset associated with a `Customer` acting as Buyer.

Its lifecycle generates business operations that must be traceable through the `Operation` and `AuditLog` Domain Models.

The services described in this document define the conceptual behavior of the Order subdomain.

Implementation details such as REST contracts, persistence mappings, JPA entities, SQL queries, MongoDB documents, HTTP clients, and infrastructure-specific mechanisms must be documented separately.

---

# Domain Model Context

An `Order` represents a purchase transaction requested by a customer.

Conceptually:

```text
MarketplaceAsset
      │
      └── Order
             │
             ├── buyer : Customer
             ├── orderLines : List<OrderLine>
             ├── totalAmount : BigDecimal
             ├── deliveryPriority : DeliveryPriority
             ├── estimatedDeliveryDays : Integer
             ├── orderStatus : OrderStatus
             ├── confirmationDate : LocalDate
             ├── fulfillmentDate : LocalDate
             ├── paymentDate : LocalDate
             ├── paidAmount : BigDecimal
             └── fulfillmentWarehouse : Warehouse
```

The buyer must be represented using the `Customer` Domain Model:

```text
Order.buyer : Customer
```

The fulfillment warehouse must be represented using the `Warehouse` Domain Model:

```text
Order.fulfillmentWarehouse : Warehouse
```

The Domain Model must not replace these relationships with primitive identifiers such as:

```text
String customerId
String warehouseId
```

Persistence adapters are responsible for translating Domain relationships into their infrastructure representation.

---

# OrderLine

Because an Order groups several purchased items, each line must be represented explicitly.

```text
OrderLine
 │
 ├── product   : Product
 ├── quantity  : Integer
 └── unitPrice : BigDecimal
```

`totalAmount` is a derived aggregate over `orderLines` and must be validated for internal consistency:

```text
totalAmount == sum(orderLine.quantity * orderLine.unitPrice for each orderLine)
```

---

# Value Objects Used by Order

The Order subdomain relies on the following Value Objects defined in the Domain Value Objects specification.

```text
Order
 │
 ├── orderStatus       : OrderStatus
 ├── deliveryPriority  : DeliveryPriority
 ├── buyer             : Customer
 │      ├── status     : CustomerStatus
 │      └── role       : SystemRole
 │
 └── fulfillmentWarehouse : Warehouse
        ├── warehouseType   : WarehouseType
        └── warehouseStatus : WarehouseStatus
```

The acting `User`, when applicable, also exposes:

```text
User
 ├── status : UserStatus
 └── role   : SystemRole
```

Business operations generated by Order services use:

```text
Operation.operationType : OperationType
```

Relevant operation types include:

```text
ORDER_CREATION
ORDER_CONFIRMATION
ORDER_CANCELLATION
ORDER_FULFILLMENT
ORDER_PAYMENT
ORDER_CLOSURE
```

---

# Value Object Validation Principles

Value Objects are part of the Domain Model and must not be treated as arbitrary strings.

For example:

```text
DeliveryPriority
OrderStatus
CustomerStatus
UserStatus
WarehouseStatus
WarehouseType
OperationType
SystemRole
```

must represent controlled business values.

The service must not validate them through arbitrary string comparisons such as:

```java
order.getOrderStatus().equals("CONFIRMED");
```

Instead, the Domain Model must work with the corresponding Value Objects.

Conceptually:

```java
order.getOrderStatus().equals(OrderStatus.CONFIRMED);
```

or, preferably, through expressive Domain behavior:

```java
order.isConfirmed();
order.canBeFulfilled();
order.canBeCancelled();
```

The exact implementation mechanism is an implementation decision, but the business concept must remain inside the Domain.

---

# DomainCatalog Rules

All catalog Value Objects inherit conceptually from:

```text
DomainCatalog
```

with:

```text
code
name
description
```

Catalog Value Objects must be:

* Immutable.
* Comparable by value.
* Restricted to valid business values.
* Identified by a unique business code.
* Independent from persistence technology.
* Independent from REST representation.

An Order service must never create arbitrary catalog values such as:

```text
new OrderStatus("ANY_VALUE")
```

unless the Domain provides a controlled factory capable of enforcing catalog invariants.

---

# Monetary Representation

All monetary attributes in the Order Domain Model remain represented as:

```text
BigDecimal
```

No `Money` Value Object is introduced by this specification, in order to remain consistent with the monetary representation adopted by the Loan subdomain.

The following attributes remain `BigDecimal`:

```text
orderLine.unitPrice : BigDecimal
totalAmount         : BigDecimal
paidAmount          : BigDecimal
```

---

# Monetary Validation Rules

The Domain must enforce the following invariants.

## Order Line Unit Price

```text
unitPrice != null
unitPrice > 0
```

## Total Amount

```text
totalAmount != null
totalAmount > 0
totalAmount == sum(orderLine.quantity * orderLine.unitPrice)
```

Zero or negative amounts are invalid.

---

## Paid Amount

Before payment registration:

```text
paidAmount == null
```

When a payment is registered:

```text
paidAmount != null
paidAmount > 0
```

Unless the business rules explicitly permit partial payments:

```text
paidAmount == totalAmount
```

The payment service must not accept an independent `BigDecimal paidAmount` parameter disconnected from the authoritative Order.

The amount must be validated against the `Order` Domain Model.

---

## BigDecimal Comparison

Because Java `BigDecimal.equals()` considers scale, Domain numerical comparisons must not rely on it when comparing monetary magnitude.

Conceptually:

```java
amount.compareTo(BigDecimal.ZERO) > 0
```

rather than:

```java
amount.equals(BigDecimal.ZERO)
```

---

## Monetary Precision

The Domain must define a consistent precision and scale policy for:

```text
unitPrice
totalAmount
paidAmount
```

This policy must be applied consistently during:

* Validation.
* Calculation.
* Persistence mapping.
* Payment processing.

Floating-point types such as:

```text
double
float
```

must never be used for monetary values.

---

# Delivery Priority Validation

`deliveryPriority` remains:

```text
DeliveryPriority
```

Valid Delivery Priorities are:

```text
STANDARD
EXPRESS
```

The Domain must validate:

```text
order.deliveryPriority != null
```

and that the value belongs to the supported `DeliveryPriority` catalog.

Each `DeliveryPriority` may define:

* Minimum/maximum estimated delivery days.
* Additional fulfillment fee constraints.
* Warehouse capability requirements.

These rules belong to the Domain.

---

# Estimated Delivery Days Validation

`estimatedDeliveryDays` remains:

```text
Integer
```

The Domain must validate:

```text
estimatedDeliveryDays != null
estimatedDeliveryDays > 0
```

Additional restrictions may depend on `DeliveryPriority`.

---

# CustomerStatus Validation

The buyer is represented by:

```text
Order.buyer : Customer
```

The Customer's status is:

```text
Customer.status : CustomerStatus
```

For normal Order processing, the buyer must satisfy:

```text
CustomerStatus.ACTIVE
```

The following states must not automatically be treated as equivalent:

```text
ACTIVE
INACTIVE
BLOCKED
```

Therefore:

```text
INACTIVE != BLOCKED
```

Unless explicitly specified otherwise:

```text
INACTIVE → cannot create new orders
BLOCKED  → cannot create new orders
ACTIVE   → may proceed subject to eligibility rules
```

---

# UserStatus Validation

When an Order operation is performed by a User, the service must validate:

```text
User.status
```

The normal requirement is:

```text
UserStatus.ACTIVE
```

A user with:

```text
INACTIVE
BLOCKED
```

must not execute protected Order operations.

User status is independent from Customer status.

For example:

```text
Customer.status = ACTIVE
User.status     = BLOCKED
```

does not authorize the User to execute an operation.

---

# SystemRole Validation

Roles are represented by:

```text
SystemRole
```

Relevant roles include:

```text
BUYER
SELLER
SUPPORT_AGENT
ACCOUNT_MANAGER
SELLER_OPERATOR
SELLER_SUPERVISOR
PLATFORM_ADMIN
```

Authorization must validate both:

```text
User.status
User.role
```

A role alone is insufficient.

For example:

```text
User.role = ACCOUNT_MANAGER
User.status = BLOCKED
```

must not authorize order confirmation.

---

# Important SystemRole Modeling Rule

`BUYER` and `SELLER` represent customer classifications more than conventional authorization roles.

If `SystemRole` is also defined as the authorization role of a `Person`, the Domain must establish how these values relate to:

```text
NaturalCustomer (Buyer)
BusinessCustomer (Seller)
```

The system must not use `SystemRole` as a substitute for determining the actual Customer subtype.

For Order eligibility, the authoritative object is:

```text
Customer
```

When a rule depends on the type of customer, the service must use the Customer Domain Model rather than inferring customer type exclusively from a role string.

---

# Order Line Eligibility

The following rules must be represented as Domain policies or specifications when applicable.

Potential business constraints per order line include:

```text
Product availability
Quantity limits
Seller-imposed minimum/maximum order quantities
Product region restrictions
```

The current specification does not define exact numerical thresholds.

Services must not invent such thresholds. They must delegate them to explicit Domain Policies/Specifications once the business rules are defined.

---

# WarehouseType and WarehouseStatus Validation

The fulfillment warehouse exposes:

```text
Warehouse.warehouseStatus : WarehouseStatus
```

Valid states are:

```text
ACTIVE
BLOCKED
CLOSED
```

Order fulfillment requires:

```text
WarehouseStatus.ACTIVE
```

The following states must reject fulfillment:

```text
BLOCKED
CLOSED
```

The Order service must not fulfill an order from a warehouse that cannot receive operations.

---

# Fulfillment Warehouse Ownership

The Order service must validate the relationship between:

```text
Order.orderLines[*].product.seller
```

and:

```text
Order.fulfillmentWarehouse
```

The service must not assume that the relationship is valid merely because both Domain Models are present.

Where the business rule requires the fulfillment warehouse to belong to the seller of the ordered products, the service must validate:

```text
Product.seller
        │
        ▼
Warehouse.owner
```

The authoritative `Warehouse` may be retrieved through the corresponding Output Port when the supplied Domain Model is incomplete or stale.

---

# Order Status Value Object

The Order uses:

```text
OrderStatus
```

The supported states are:

```text
CREATED
CONFIRMED
FULFILLED
PAID
CLOSED
CANCELLED
```

The Domain must be the authority for valid transitions.

---

# Order Lifecycle

The lifecycle is:

```text
                 ┌──────────────► CANCELLED
                 │
CREATED ─────────┤
                 │
                 ▼
             CONFIRMED
                 │
                 ├──────────────► CANCELLED
                 │
                 ▼
             FULFILLED
                 │
                 ▼
               PAID
                 │
                 ▼
               CLOSED
```

Cancellation is only permitted while the Order is `CREATED` or `CONFIRMED`. Once `FULFILLED`, cancellation is no longer permitted under the current lifecycle — this mirrors the Loan subdomain's rule that a `DISBURSED` loan cannot be simply cancelled without addressing outstanding obligations.

---

# State Transition Rules

The Domain must enforce:

```text
CREATED   → CONFIRMED
CREATED   → CANCELLED

CONFIRMED → FULFILLED
CONFIRMED → CANCELLED

FULFILLED → PAID

PAID      → CLOSED
```

Invalid transitions must raise:

```text
InvalidOrderStatusTransitionException
```

The persistence layer must never determine whether a transition is valid.

---

# Lifecycle Ownership

The service must never allow an external caller to arbitrarily assign:

```text
orderStatus
confirmationDate
fulfillmentDate
paymentDate
```

For example, a request must not be trusted merely because it contains:

```text
orderStatus = CONFIRMED
```

The service must establish the correct initial state through Domain behavior.

Likewise, `confirmationDate`, `fulfillmentDate`, and `paymentDate` must each be established by the Domain at the moment of the corresponding valid transition, never supplied by the caller.

---

# Standard Order Service Pattern

Every state-changing Order service must follow the following conceptual pattern:

```text
1. Receive Domain Models
        │
        ▼
2. Retrieve authoritative state when necessary
        │
        ▼
3. Validate User
        │
        ▼
4. Validate Customer
        │
        ▼
5. Validate User-Customer relationship
        │
        ▼
6. Validate Order
        │
        ▼
7. Validate Value Objects
        │
        ▼
8. Validate Order status
        │
        ▼
9. Validate operation-specific business rules
        │
        ▼
10. Execute Domain behavior
        │
        ▼
11. Persist Domain Model
        │
        ▼
12. Create Operation
        │
        ▼
13. Create AuditLog
```

Not every service requires every step. Only relevant validations must be executed.

The service must not introduce artificial validation use cases such as:

```text
ValidateUserService
ValidateOwnershipService
ValidateOrderStatusService
ValidateWarehouseService
```

when those validations are part of a larger cohesive business operation.

---

# Authoritative State Rule

For state-changing operations, the Order supplied to the service represents the business context but must not automatically be considered the authoritative persisted state.

When required, the service retrieves the authoritative Order through:

```text
OrderRepository
```

Conceptually:

```text
Incoming Order
     │
     ▼
OrderRepository
     │
     ▼
Authoritative Order
     │
     ▼
Business Validation
     │
     ▼
Domain Behavior
```

This prevents stale Domain Models from causing invalid state transitions.

# 1. Create Order

## Description

Creates a new order for a Customer.

The order enters:

```text
CREATED
```

The caller must not arbitrarily determine the initial lifecycle state.

---

## Input

```java
Order create(Order order);
```

The Domain Model must contain:

```text
Buyer
OrderLines
DeliveryPriority
EstimatedDeliveryDays when applicable
```

---

## User Validation

If the request is initiated by an authenticated User, the service must validate:

```text
User.status == ACTIVE
```

and the appropriate authorization rule.

If the request is customer-initiated, the service must validate:

```text
User
   │
   ▼
Customer
   │
   ▼
Order.buyer
```

The requesting Customer must correspond to the buyer.

---

## Customer Validation

Validate:

```text
order.buyer != null
order.buyer.status != null
order.buyer.status == CustomerStatus.ACTIVE
```

Additional Customer information must be obtained through:

```text
CustomerRepository
```

only when it is not already available in the Domain Model.

---

## Order Line Validation

Validate that every `orderLine`:

```text
product != null and exists
quantity != null and quantity > 0
unitPrice != null and unitPrice > 0
```

and that:

```text
totalAmount == sum(orderLine.quantity * orderLine.unitPrice)
```

---

## Delivery Priority Validation

Validate:

```text
deliveryPriority != null
```

and ensure that the value belongs to the supported `DeliveryPriority` catalog.

---

## Initial Status

The service must establish:

```text
CREATED
```

through Domain behavior.

The caller must not be able to create an already-confirmed order.

---

## Persistence

Persist through:

```text
OrderRepository
```

---

## Operation

Generate:

```text
OperationType.ORDER_CREATION
```

---

## Audit

Create the corresponding `AuditLog`.

---

# 3. Evaluate Order

## Description

Evaluates whether an Order satisfies the Domain conditions necessary to proceed toward confirmation or cancellation.

Evaluation should be conceptually separated from the actual state-changing confirmation or cancellation operation.

---

## Input

```text
OrderEvaluationResult evaluate(Order order)
```

This is recommended when the evaluation must communicate a business decision without mutating the Order.

---

## Status Validation

The Order must be:

```text
CREATED
```

An Order already:

```text
CONFIRMED
FULFILLED
PAID
CLOSED
CANCELLED
```

must not be evaluated as a new application.

---

## Customer Validation

Validate:

```text
Buyer exists
Buyer is ACTIVE
Buyer is eligible
```

---

## Order Line Validation

Validate that every product remains available and every unit price remains valid.

---

## Evaluation Result

The Domain may produce:

```text
ConfirmationDecision.CONFIRMED
ConfirmationDecision.CANCELLED
```

Conceptually:

```text
Evaluate Order
       │
       ▼
ConfirmationDecision
       │
       ├── CONFIRMED ──► Confirm Order
       │
       └── CANCELLED ──► Cancel Order
```

This avoids duplicating confirmation/cancellation responsibilities.

---

# 4. Confirm Order

## Description

Confirms an Order that is currently created.

The operation is restricted to:

```text
ACCOUNT_MANAGER
```

or the Buyer, when self-confirmation is permitted by the business rules.

---

## Input

```java
Order confirm(User user, Order order);
```

---

## User Validation

Validate:

```text
user != null
user.status == UserStatus.ACTIVE
user.role == SystemRole.ACCOUNT_MANAGER   (or the requesting Buyer's own SystemRole.BUYER)
```

---

## Customer Validation

Validate:

```text
order.buyer != null
order.buyer.status == CustomerStatus.ACTIVE
```

---

## Order Status Validation

The authoritative Order must be:

```text
CREATED
```

Only:

```text
CREATED → CONFIRMED
```

is permitted.

---

## Order Line Validation

Validate that every `orderLine` still references an available product at a valid price.

---

## Confirmation Date

The Domain establishes `confirmationDate` at the moment of the valid transition. The caller must not supply or override this date.

---

## Domain Behavior

```text
order.confirm(...)
```

The application service must not simply execute:

```java
order.setOrderStatus(OrderStatus.CONFIRMED);
```

without Domain transition rules.

---

## Persistence

Persist through:

```text
OrderRepository
```

---

## Operation

Generate:

```text
ORDER_CONFIRMATION
```

---

## Audit

Persist the corresponding audit record.

# 6. Fulfill Order

## Description

Allocates the ordered items from the designated Warehouse and decreases stock accordingly.

This is a state-changing operation that crosses into the Inventory subdomain and therefore requires strict validation and transactional consistency.

---

## Input

```java
Order fulfill(User user, Order order, Warehouse warehouse);
```

---

## Order Status Validation

The authoritative Order must be:

```text
CONFIRMED
```

The only permitted transition is:

```text
CONFIRMED → FULFILLED
```

---

## Warehouse Validation

Validate:

```text
warehouse != null
warehouse.warehouseStatus == ACTIVE
```

and retrieve authoritative warehouse information when necessary.

---

## Ownership Validation

The Domain must validate the relationship between the ordered products' seller and the fulfillment warehouse's owner when the business requires the warehouse to belong to the seller of the products.

---

## Stock Sufficiency Validation

For every `orderLine`:

```text
orderLine.quantity <= availableStock(warehouse, orderLine.product)
```

Otherwise:

```text
InsufficientStockException
```

must be raised.

---

## Duplicate Fulfillment Validation

An Order must not be fulfilled more than once.

The service must validate:

```text
OrderStatus != FULFILLED
```

and the authoritative persisted state must be checked. The operation must also be protected against concurrent duplicate execution.

---

## Warehouse Domain Behavior

The service must not modify warehouse stock directly through infrastructure.

Conceptually:

```text
Order
 │
 ▼
Fulfill Order
 │
 ├── Validate Order
 │
 ├── Validate Warehouse
 │
 ├── Decrease Warehouse stock
 │
 └── Transition Order
```

---

## Cross-Aggregate Consideration

`Order` and `Warehouse` are separate Domain Models.

If they are separate Aggregates, the Order service must not bypass Warehouse's business rules by directly modifying the Warehouse aggregate.

A preferred conceptual approach is:

```text
Order Service
      │
      ▼
Inventory application/domain operation
      │
      ▼
Warehouse
```

or an appropriate `InventoryAdjustmentPort` representing the business capability required to decrease stock.

---

## Fulfillment Date

The Domain establishes `fulfillmentDate` when the fulfillment successfully occurs. The caller must not provide this date.

---

## Transactional Consistency

The following changes must be consistent:

```text
Order → FULFILLED
Warehouse stock → decreased
Operation → ORDER_FULFILLMENT
AuditLog → recorded
```

The system must prevent situations such as:

```text
Order = FULFILLED
Warehouse stock = not decreased
```

or:

```text
Warehouse stock = decreased
Order = CONFIRMED
```

---

## Operation

Generate:

```text
ORDER_FULFILLMENT
```

---

## Audit

Generate the corresponding audit event.

---

# Evaluation vs Eligibility

The following distinction must be maintained:

```text
Validate Order Eligibility
        │
        ▼
Determines whether business prerequisites are satisfied
```

while:

```text
Evaluate Order
        │
        ▼
Performs the broader confirmation evaluation
        │
        ▼
ConfirmationDecision
```

Eligibility does not necessarily imply confirmation. The final confirmation decision remains a separate business action.

| Consult Status          | ACTIVE                      | Authorization-dependent   | Access rule      | N/A        | Authoritative                 | N/A                           | N/A                    | None                |
| Consult Details         | ACTIVE                      | Authorization-dependent   | Access rule      | N/A        | Authoritative                 | N/A                           | N/A                    | None                |
| Validate Eligibility    | ACTIVE when actor exists    | Authorization-dependent   | ACTIVE           | Required   | Applicable                    | ACTIVE if required            | Amount > 0             | None                |

# Domain Behavior

The Order Domain Model should expose business behavior instead of unrestricted setters.

```text
Order
 │
 ├── confirm()
 ├── cancel()
 ├── fulfill(warehouse)
 ├── registerPayment(amount)
 └── close()
```

The Domain methods are responsible for enforcing valid state transitions.

For example:

```text
order.confirm()
```

must internally ensure:

```text
orderStatus == CREATED
```

before transitioning to:

```text
CONFIRMED
```

Likewise:

```text
order.fulfill(warehouse)
```

must only be valid when:

```text
orderStatus == CONFIRMED
```

# Operation and Audit Pattern

Every significant Order lifecycle operation follows:

```text
Business Action
      │
      ▼
Domain State Change
      │
      ├──────────────► Order
      │
      ▼
Operation
      │
      ▼
AuditLog
```

For example:

```text
Confirm Order
     │
     ├── Order → CONFIRMED
     │
     ├── Operation → ORDER_CONFIRMATION
     │
     └── AuditLog
```

The Order service must not directly manipulate the persistence representation of either `Operation` or `AuditLog`.

---

# Operation Consistency

An Operation must represent an actual business action.

The service must not create `ORDER_FULFILLMENT` if the Order was not successfully fulfilled. Likewise, `ORDER_PAYMENT` must not be created if the payment was not successfully registered.

Operation creation must therefore occur as part of the same consistent business transaction/process.

---

# Audit Requirements

Audit information should allow the system to determine at minimum:

```text
What operation occurred?
Which Order was affected?
Who or what performed it?
When did it occur?
What was the relevant business state?
```

The exact structure belongs to the Audit domain. The Order service is responsible for invoking the appropriate audit Output Port.

# Architectural Constraints

1. `Order` is a Domain Model.
2. `Order` inherits from `MarketplaceAsset`.
3. `Order.buyer` is represented by `Customer`.
4. `Order.fulfillmentWarehouse` is represented by `Warehouse`.
5. Customer relationships must not be represented only by primitive identifiers.
6. Warehouse relationships must not be represented only by primitive identifiers.
7. Order services must receive Domain Models or Value Objects.
8. Order services must not receive primitive identifiers as application-level parameters.
9. Order services must not receive isolated attributes when those attributes belong to a Domain Model.
10. REST DTOs must never enter the Domain layer.
11. Persistence entities must never enter the Domain layer.
12. Business validations must be implemented in the appropriate Domain/Application components.
13. Value Objects must enforce their own structural/business invariants.
14. Controlled catalog values must not be replaced with arbitrary strings.
15. `OrderStatus` must be treated as a controlled Domain Value Object.
16. `DeliveryPriority` must be treated as a controlled Domain Value Object.
17. `WarehouseStatus` must be treated as a controlled Domain Value Object.
18. `CustomerStatus` must be treated as a controlled Domain Value Object.
19. `UserStatus` must be treated as a controlled Domain Value Object.
20. `SystemRole` must be treated as a controlled Domain Value Object.
21. `OperationType` must be treated as a controlled Domain Value Object.
22. `ConfirmationDecision` is a primitive enum and must not be confused with `OrderStatus`.
23. Monetary values must remain `BigDecimal`.
24. `double` and `float` must not be used for monetary values.
25. Order line unit prices must be greater than zero.
26. Total amount must equal the sum of order line subtotals.
27. Paid amount must equal the total amount unless partial payments are explicitly permitted.
28. Estimated delivery days must be positive.
29. Fulfillment warehouse ownership must be validated when required by business rules.
30. Order-line-specific rules must be implemented through Domain policies/specifications when required.
31. User status must be validated before protected User operations.
32. Customer status must be validated before customer eligibility operations.
33. Authorization must validate both User status and role.
34. Order confirmation requires `ACCOUNT_MANAGER` (or self-confirmation by the `BUYER`, when explicitly permitted).
35. Order status transitions must be enforced by the Domain.
36. `CREATED` is the initial Order lifecycle state.
37. A cancelled Order must not be fulfilled.
38. An Order must not be fulfilled before confirmation.
39. An Order must not be fulfilled more than once.
40. An Order must not be paid before fulfillment.
41. An Order must not be closed before payment.
42. An Order must not be cancelled from an invalid state.
43. Confirmation date must be established by the Domain transition.
44. Fulfillment date must be established by the Domain transition.
45. Payment date must be established by the Domain transition.
46. Callers must not arbitrarily control lifecycle dates.
47. Callers must not arbitrarily control lifecycle status.
48. Authoritative persisted state must be retrieved when required for state-changing operations.
49. Order services must use Output Ports for external information.
50. Order services must never access MySQL directly.
51. Order services must never access MongoDB directly.
52. Order services must never execute SQL directly.
53. Order services must never access JPA directly.
54. Persistence adapters must remain responsible for persistence translation.
55. `OrderRepository` is responsible for Order persistence.
56. `CustomerRepository` provides Customer information when required.
57. `ProductRepository` provides Product information when required.
58. `WarehouseRepository`/`InventoryAdjustmentPort` provides Warehouse information and stock adjustment when required.
59. `OperationRepository` persists business operations.
60. `AuditRepository` persists audit information.
61. Significant Order lifecycle events must generate an `Operation`.
62. Relevant Order operations must be recorded in the `AuditLog`.
63. An Operation must correspond to an actual successful business action.
64. Order state changes and their corresponding operations/audits must maintain transactional consistency.
65. Order must not directly manipulate warehouse stock in persistence.
66. Warehouse business behavior must be respected when decreasing stock during fulfillment.
67. Cross-Aggregate interactions must respect Aggregate boundaries.
68. The Domain must remain independent of infrastructure technology.
69. The Order subdomain must be testable without MySQL.
70. The Order subdomain must be testable without MongoDB.
71. The Order subdomain must be testable without REST.
72. The Order subdomain must be testable without JPA.
73. The persistence layer must never determine business status transitions.
74. Controllers must not contain Order business rules.
75. DTO mappers must not contain Order business rules.
76. Repository adapters must not contain Order business rules.
